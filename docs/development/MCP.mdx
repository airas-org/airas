AIRAS provides a local MCP (Model Context Protocol) server that exposes research subgraphs as tools for MCP clients such as Claude Code and Claude Desktop.

## Setup

No installation is required — `uvx` fetches the package on first run. The only prerequisite is [uv](https://docs.astral.sh/uv/).

### 1. Credentials

Credentials live in `~/.airas/credentials.json`. The file is re-read on every tool call, so you can create or edit it at any time — even after the server is already registered and running.

Create or edit the file by hand:

```bash
mkdir -p ~/.airas
cat > ~/.airas/credentials.json <<'EOF'
{
  "OPENAI_API_KEY": "sk-...",
  "GH_PERSONAL_ACCESS_TOKEN": "ghp_..."
}
EOF
chmod 600 ~/.airas/credentials.json
```

| Key | Required | Purpose |
| --- | --- | --- |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` / `OPENROUTER_API_KEY` / `VERCEL_AI_GATEWAY_API_KEY` / `RIKYU_API_KEY` | At least one | LLM calls (query generation, paper extraction, hypothesis generation, paper writing) |
| `GH_PERSONAL_ACCESS_TOKEN` | For repository / experiment / paper-reproduction / publication tools | GitHub API access (`repo` + `workflow` scopes) |

If a tool is called before its credential is configured, it returns an error pointing at this file.

### Seyval compute platform

`dispatch_experiment(backend="seyval")`, `import_run_outputs(backend="seyval")` and the record gate's provenance cross-check run against Seyval, which takes its own key:

```json
{
  "SEYVAL_API_KEY": "seyval_pat_...",
  "SEYVAL_COMPUTE_ID": "byo:<uuid>"
}
```

`SEYVAL_COMPUTE_ID` is optional and names the default cluster; without it, runs go to Seyval-managed compute. `SEYVAL_WORKSPACE_ID` is required when the key sees several workspaces (a repository is registered into one for good). `SEYVAL_BASE_URL` overrides the API host.

Seyval was previously called AIXS. If you configured it under the old names, rename `AIXS_API_KEY` / `AIXS_BASE_URL` / `AIXS_COMPUTE_ID` to `SEYVAL_*`, reissue the key so it is a `seyval_pat_` one, and pass `backend="seyval"` instead of `backend="aixs"`. The old names are no longer read.

### OpenAI-compatible endpoints (Rikyu)

RIKEN R-CCS's Rikyu API speaks the OpenAI API, and is reached with one credential:

```json
{
  "RIKYU_API_KEY": "..."
}
```

Address its models as `rikyu/<model>`, where `<model>` is an ID the endpoint itself reports:

```bash
curl -H "Authorization: Bearer $RIKYU_API_KEY" \
  https://api.rikyu.r-ccs.riken.jp/v1/models
```

The base URL defaults to `https://api.rikyu.r-ccs.riken.jp/v1`; add `RIKYU_API_BASE` to the credentials file by hand to point at a different host. A future OpenAI-compatible endpoint would get its own provider name and key the same way (see the `RIKYU_*` wiring in `backend/src/airas/infra/llm_provider_resolver.py`), so a key always says which host it reaches and which project is billed.

The same key reaches the coding agent. To use the endpoint from a local [opencode](https://opencode.ai), declare it as a custom provider in `~/.config/opencode/opencode.json` (the experiment repository ships the equivalent block in `.opencode/opencode.jsonc`, and its workflows pass the key through from repository secrets):

```json
{
  "provider": {
    "rikyu": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Rikyu (RIKEN R-CCS)",
      "options": {
        "baseURL": "https://api.rikyu.r-ccs.riken.jp/v1",
        "apiKey": "{env:RIKYU_API_KEY}"
      },
      "models": {
        "kimi-k3": { "name": "Kimi K3" }
      }
    }
  }
}
```

Register one entry under `models` per model ID you want to select, then run `opencode run --model rikyu/<model>` — the same name the node LLMs use. Coding-agent use requires the endpoint to serve tool calls (on vLLM, a tool-call parser must be enabled); a model that only handles plain completions still works for node LLM calls.

### 2. Register the server (Claude Code)

```bash
claude mcp add airas -- uvx airas
```

Or add it to your project's `.mcp.json`:

```json
{
  "mcpServers": {
    "airas": {
      "command": "uvx",
      "args": ["airas"]
    }
  }
}
```

## Tools

### Paper discovery & hypothesis

| Tool | Description |
| --- | --- |
| `get_prompts` | The prompt for an authoring step (`hypothesis_and_design` / `experiment_code` / `experiment_analysis` / `paper_writing`) so the MCP host writes the result itself; `experiment_analysis` renders from the clone (`local_path`), the same prompt `analyze_experiment` sends; no API keys required |
| `search_papers` | Multi-source paper search (OpenAlex / Semantic Scholar / arXiv / AIRAS DB) with normalized, de-duplicated results; no API keys required |
| `fetch_paper_fulltext` | Fetch a paper's full text by arXiv ID, DOI, or PDF URL (legal open-access resolution only); no API keys required |
| `retrieve_models` | Check first: AIRAS's hand-curated candidate models for a subfield (vetted defaults with runnable code); no API key required |
| `retrieve_datasets` | Check first: AIRAS's hand-curated candidate datasets for a subfield; no API key required |
| `search_huggingface_hub` | Fallback when the curated tools have no fit: live Hugging Face Hub search for models/datasets by task/query, returned in the same shape as the curated tools; no API key required |
| `get_library_docs` | Look up canonical documentation endpoints (official docs / source repo / `llms.txt`) for ~165 AI research libraries, filterable by `domain` / `category`; no API key required |

### Experiment execution

| Tool | Description |
| --- | --- |
| `prepare_repository` | Create the experiment repository from the template, protect the branch (the record gate as a required check), enable Pages |
| `set_github_actions_secrets` | Copy this machine's API keys into the repository's Actions secrets |
| `dispatch_experiment` | Start a sanity-check or main experiment run (async) on GitHub Actions or the Seyval compute platform (`backend` parameter) |
| `get_workflow_runs` | Check the status of recent workflow runs (non-blocking) |
| `get_experiment_run_status` | Check one run on any backend and fetch its stdout/stderr tails for error diagnosis |
| `import_run_outputs` | Copy a finished run's outputs from the backend's store (Seyval storage or the workflow artifact) into `.research/results/` with a provenance manifest |
| `fetch_experiment_results` | Read what the runs left under `.research/results/` in the clone: per run its metrics, evaluation report, figures and provenance entry |
| `download_workflow_artifacts` | Download artifacts of a specific workflow run |
| `analyze_experiment` | Draft the analysis per claim from the record and the run outputs with a backend LLM (`model`); `get_prompts(step="experiment_analysis")` is the same prompt for writing it yourself |
| `render_chart` | Render a Vega-Lite spec to a figure file (PDF/SVG/PNG) locally; no API keys required |
| `render_diagram` | Render a text diagram (mermaid, graphviz, d2, plantuml, …) via Kroki; no API keys required |

### Research record & paper

| Tool | Description |
| --- | --- |
| `preregister_record` | Create `.research/record.json` before any run: the literature (pinned by DOI / arXiv id, full text snapshotted, quotes checked) and the hypotheses with their claims, criteria, predictions and runs, in one freeze commit; also writes `claims.tex` and `references.bib` |
| `append_to_record` | Append to the record (append-only: revise with the same id, retire with `withdrawn`); literature, hypotheses, claims, tables, charts, passages, and with `run_results` the results derived from the run outputs |
| `update_record` | Derive each run's result and each claim's verdict from `.research/results/`, render `values.tex` and `tables/`, and commit |
| `verify_latex` | Build the paper locally (lualatex for CJK) and report undefined citations / references, missing figures and errors; pass `local_path`; `output_path` keeps the PDF |
| `verify_paper_values` | The paper gate as CI runs it: declarations, append-only history, values.tex / claims.tex regeneration, `\airasval` keys, citations; with `model`, judges every unjudged passage citation and writes the judgments into the record |
| `open_in_overleaf` | Create a link that opens the paper in Overleaf; pass `local_path` to export the local working tree without pushing |
| `get_available_llms` | Which LLM providers the configured keys allow, for `model` arguments |

### Paper reproduction (GitHub Actions)

| Tool | Description |
| --- | --- |
| `dispatch_paper_reproduction_generate` | Generate stage: an agent picks a figure/table from the paper (guided by `instruction`) and writes Hydra config + `src/main.py` under `.reproduction/<repro_id>/`, returning `repro_id` (async, does not run it) |
| `dispatch_paper_reproduction_run` | Run stage: agentless `python -m src.main` via Hydra, producing the figure/table + result.json (async) |
| `fetch_paper_reproduction_results` | Fetch results and validate them on the AIRAS side (deterministic pitfall/parameter checks + LLM judge) |
| `dispatch_parameter_tuning_run` | Sweep the config's `optuna.search_space` with Optuna (TPE), reusing `src/main.py` via Hydra overrides — no code generation (async) |
| `fetch_parameter_tuning_results` | Fetch the results (best parameters, optimization figure) of a completed tuning run |

Authoring steps have two lanes. The agent writes the result itself, guided by the skills, with the step's prompt from `get_prompts` (`hypothesis_and_design`, `experiment_code`, `experiment_analysis`, `paper_writing`; no key required); the one backend-LLM tool that shares one of these prompts is `analyze_experiment` (requires a provider key), which answers the `experiment_analysis` prompt; `verify_paper_values` with `model` uses its own citation-judging prompt. Every prompt comes with an `output_json_schema` describing the data format to produce and a `flow` note on where it goes.

A typical paper-reproduction flow: `prepare_repository` (once, to create a runner repository from
airas-template) → `set_github_actions_secrets` → `dispatch_paper_reproduction_generate` (returns
`repro_id`; every later reproduction tool requires it) → (poll `get_workflow_runs`) → `dispatch_paper_reproduction_run` → (poll) → `fetch_paper_reproduction_results` → (optionally) `dispatch_parameter_tuning_run` (poll) → `fetch_parameter_tuning_results`. Each reproduction lives in its own `.reproduction/<repro_id>/` directory, so one branch can hold multiple reproductions.

A typical flow (the `auto-research` skill holds the order and the invariants): `prepare_repository` → `set_github_actions_secrets` → `search_papers` → `fetch_paper_fulltext` (read the files) → **write the hypothesis and the design yourself** (`get_prompts(step="hypothesis_and_design")`) → `preregister_record` (the freeze commit) → **write the preregistration paper** (`get_prompts(step="paper_writing")`) → `verify_latex` → push to the staging ref, fast-forward when the gate is green → **write the experiment code yourself** (`get_prompts(step="experiment_code")`, see below) → `dispatch_experiment` → (poll `get_experiment_run_status`) → `import_run_outputs` → `fetch_experiment_results` → `update_record` → **analyse** (`get_prompts(step="experiment_analysis")` or `analyze_experiment`) → **create figures** (`render_chart`, see below) → **fill Results and Discussion** → `verify_paper_values` with `model` → `verify_latex` → push; CI re-verifies and the Publish Paper workflow builds and commits the PDF of record. `open_in_overleaf` hands the project to the user for editing (with `local_path`, no push needed).

### Writing the experiment code

The MCP host is expected to be a capable coding agent (Claude Code, Cursor, ...), so AIRAS does not generate the experiment code for you. After `prepare_repository`:

1. Clone the experiment repository locally with git.
2. Read the contract from `get_prompts(step="experiment_code")` — the allowed files, the CLI shape, the `sanity` / `pilot` / `full` modes and their validation lines, and the three files verification reads; the run ids and metrics it binds you to are in `.research/record.json`.
3. For any library the design relies on, call `get_library_docs` and fetch the returned `llms.txt` (or docs) to work from current APIs rather than memory.
4. Implement the experiment, run `mode=sanity` locally until it prints `SANITY_VALIDATION: PASS`, then commit and push.
5. Dispatch GPU-scale runs with `dispatch_experiment` and fetch errors/results with `get_experiment_run_status` / `fetch_experiment_results`.

Headless pipelines (the built-in autonomous research workflows) still generate code remotely on GitHub Actions; that path is not exposed as an MCP tool.

### Creating figures and diagrams

Result figures and method diagrams are also created by the MCP host itself rather than on GitHub Actions:

1. Fetch the experiment results with `fetch_experiment_results` (or read them from your local clone — run directories live under `.research/results/`).
2. Build a Vega-Lite spec from the results and render it with `render_chart`, saving the PDF under `.research/results/chart/` in the clone. For method diagrams, write the diagram as text (mermaid, graphviz, d2, …) and render it with `render_diagram` into `.research/results/diagram/`. (Generating figures yourself, e.g. with matplotlib, works too — only the output location matters.)
3. `render_chart` appends the chart's spec to the record and commits it. No copy step is needed: the paper build (`verify_latex`, the Publish Paper workflow) and `open_in_overleaf` automatically pick up every figure PDF under `.research/results/` and `.research/diagrams/`, exposed to LaTeX as `images/<path relative to that directory>` (e.g. `.research/results/chart/loss.pdf` → `images/chart/loss.pdf`) with the directory structure preserved. Reference figures accordingly in the paper.

`render_chart` renders entirely locally. `render_diagram` uses the public https://kroki.io by default; set `KROKI_BASE_URL` to a self-hosted Kroki instance to keep unpublished diagrams on-premises.

As with code generation, the autonomous research workflows still run visualization and diagram generation on GitHub Actions; those paths are not exposed as MCP tools.

Long-running steps return immediately instead of blocking. Experiments run on GitHub Actions or on Seyval depending on `dispatch_experiment`'s `backend`; either way it returns an `execution_id`, which `get_experiment_run_status` tracks and `import_run_outputs` collects. The record and paper gates and the Publish Paper build run on GitHub Actions; track them with `get_workflow_runs`.

## Development

Run the server from a checkout:

```bash
cd backend
uv sync
uv run airas
```

The server uses stdio transport; it is started on demand by the MCP client and requires no database or web server.
