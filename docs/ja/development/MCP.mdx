AIRASは、Claude CodeやClaude DesktopなどのMCPクライアントから研究サブグラフをツールとして利用できる、ローカルMCP（Model Context Protocol）サーバーを提供しています。

## セットアップ

インストール作業は不要です。初回実行時に `uvx` がパッケージを取得します。前提条件は [uv](https://docs.astral.sh/uv/) がインストールされていることだけです。

### 1. 認証情報の設定

認証情報は `~/.airas/credentials.json` に置きます。このファイルは**ツール呼び出しのたびに読み込まれる**ので、サーバー登録後・起動後にいつでも作成・編集できます。

ファイルを手動で作成・編集します：

```bash
mkdir -p ~/.airas
cat > ~/.airas/credentials.json <<'EOF'
{
  "OPENAI_API_KEY": "sk-...",
  "GH_PERSONAL_ACCESS_TOKEN": "ghp_..."
}
EOF
chmod 600 ~/.airas/credentials.json
```

| キー | 必須 | 用途 |
| --- | --- | --- |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` / `OPENROUTER_API_KEY` / `VERCEL_AI_GATEWAY_API_KEY` / `RIKYU_API_KEY` | いずれか1つ | LLM呼び出し（クエリ生成・論文抽出・仮説生成・論文執筆） |
| `GH_PERSONAL_ACCESS_TOKEN` | リポジトリ・実験・出版系ツール使用時 | GitHub APIアクセス（`repo` + `workflow` スコープ） |

認証情報が未設定のままツールを呼ぶと、このファイルを案内するエラーが返ります。

### Seyval 計算基盤

`dispatch_experiment(backend="seyval")`、`import_run_outputs(backend="seyval")`、および record gate の provenance 照合は Seyval に対して動作し、専用のキーが必要です：

```json
{
  "SEYVAL_API_KEY": "seyval_pat_...",
  "SEYVAL_COMPUTE_ID": "byo:<uuid>"
}
```

`SEYVAL_COMPUTE_ID` は任意で、デフォルトのクラスタを指定します。未設定の場合は Seyval 管理の計算資源で実行されます。キーが複数のワークスペースを見られる場合は `SEYVAL_WORKSPACE_ID` が必須です（リポジトリは登録先のワークスペースから移せません）。`SEYVAL_BASE_URL` で API のホストを上書きできます。

Seyval は以前 AIXS という名称でした。旧名で設定している場合は、`AIXS_API_KEY` / `AIXS_BASE_URL` / `AIXS_COMPUTE_ID` を `SEYVAL_*` にリネームし、キーを `seyval_pat_` 形式で再発行し、`backend="aixs"` の代わりに `backend="seyval"` を渡してください。旧名は読み込まれません。

### OpenAI互換エンドポイント（理究）

理研R-CCSの理究APIはOpenAI互換で、認証情報は1つだけです：

```json
{
  "RIKYU_API_KEY": "..."
}
```

モデル名は `rikyu/<model>` の形式で指定します。`<model>` はエンドポイント自身が返すモデルIDです：

```bash
curl -H "Authorization: Bearer $RIKYU_API_KEY" \
  https://api.rikyu.r-ccs.riken.jp/v1/models
```

base URLは `https://api.rikyu.r-ccs.riken.jp/v1` がデフォルトです。別のホストを指す場合は、認証情報ファイルに `RIKYU_API_BASE` を手動で追加してください。将来別のOpenAI互換エンドポイントを追加する場合も同様に、固有のプロバイダー名とキーを与えます（`backend/src/airas/infra/llm_provider_resolver.py` の `RIKYU_*` の配線を参照）。こうすることで、キー名から接続先と課金先が常に辿れます。

同じキーでコーディングエージェントからも利用できます。ローカルの [opencode](https://opencode.ai) から使う場合は、`~/.config/opencode/opencode.json` にカスタムプロバイダーとして宣言します（実験リポジトリ側には同等の設定が `.opencode/opencode.jsonc` に含まれており、ワークフローがリポジトリシークレットからキーを渡します）：

```json
{
  "provider": {
    "rikyu": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Rikyu (RIKEN R-CCS)",
      "options": {
        "baseURL": "https://api.rikyu.r-ccs.riken.jp/v1",
        "apiKey": "{env:RIKYU_API_KEY}"
      },
      "models": {
        "kimi-k3": { "name": "Kimi K3" }
      }
    }
  }
}
```

選択したいモデルIDごとに `models` へ1エントリを追加し、`opencode run --model rikyu/<model>` で実行します（ノード内LLMと同じ名前です）。コーディングエージェント用途ではエンドポイント側がツールコールに対応している必要があります（vLLMの場合はツールコールパーサーの有効化が必要）。対応していないモデルでも、ノード内LLMとしては利用できます。

### 2. サーバーの登録（Claude Code）

```bash
claude mcp add airas -- uvx airas
```

またはプロジェクトの `.mcp.json` に追加します：

```json
{
  "mcpServers": {
    "airas": {
      "command": "uvx",
      "args": ["airas"]
    }
  }
}
```

## ツール

### 論文探索・仮説生成

| ツール | 説明 |
| --- | --- |
| `get_prompts` | 執筆ステップ（`hypothesis_and_design` / `experiment_code` / `experiment_analysis` / `paper_writing`）のプロンプトを返し、MCP ホスト自身が書く。`experiment_analysis` は clone（`local_path`）から描画し、`analyze_experiment` が送るものと同じ文面。APIキー不要 |
| `search_papers` | 複数ソース（OpenAlex / Semantic Scholar / arXiv / AIRAS DB）の並列論文検索。結果は正規化・重複排除済み。APIキー不要 |
| `fetch_paper_fulltext` | arXiv ID / DOI / PDF URL から論文全文を取得（合法なオープンアクセス解決のみ）。APIキー不要 |
| `retrieve_models` | サブ分野ごとの候補モデル一覧を取得。APIキー不要 |
| `retrieve_datasets` | まず参照: サブ分野ごとの AIRAS 厳選候補データセット一覧。APIキー不要 |
| `search_huggingface_hub` | 厳選側に該当がない場合のフォールバック: Hugging Face Hub をライブ検索し、厳選ツールと同じ形式で候補を返す。APIキー不要 |
| `get_library_docs` | AI研究ライブラリ約165件の公式ドキュメント / ソースリポジトリ / `llms.txt` エンドポイントを検索（`domain` / `category` で絞り込み可）。APIキー不要 |

### 実験実行

| ツール | 説明 |
| --- | --- |
| `prepare_repository` | テンプレートから実験リポジトリを作成し、ブランチ保護（record gate を必須チェックに）と Pages を設定 |
| `set_github_actions_secrets` | このマシンの API キーをリポジトリの Actions secrets にコピー |
| `dispatch_experiment` | サニティチェック／本実験の実行を開始（非同期）。`backend` パラメータで GitHub Actions / Seyval 計算基盤を選択 |
| `get_workflow_runs` | 直近のワークフロー実行のステータス確認（ノンブロッキング） |
| `get_experiment_run_status` | 任意のバックエンドの実行1件のステータス確認と stdout/stderr の取得（エラー診断用） |
| `import_run_outputs` | 完了した実行の出力をバックエンドの保存先（Seyval のストレージ、または workflow の artifact）から `.research/results/` に provenance マニフェスト付きで取り込む |
| `fetch_experiment_results` | clone の `.research/results/` を読む: run ごとの metrics、評価レポート、図、provenance エントリ |
| `download_workflow_artifacts` | 特定のワークフロー実行のアーティファクトを取得 |
| `analyze_experiment` | record と run 出力から claim ごとの分析の下書きをバックエンド LLM（`model`）で作る。自分で書くなら `get_prompts(step="experiment_analysis")` が同じプロンプト |
| `render_chart` | Vega-Lite仕様を図ファイル（PDF/SVG/PNG）にローカルでレンダリング。APIキー不要 |
| `render_diagram` | テキスト記法のダイアグラム（mermaid, graphviz, d2, plantuml など）をKroki経由でレンダリング。APIキー不要 |

### 研究記録・論文

| ツール | 説明 |
| --- | --- |
| `preregister_record` | 実験前に `.research/record.json` を作る: 文献（DOI / arXiv id で固定、全文をスナップショット、引用を照合）と仮説・claim・criterion・prediction・run を 1 回の freeze commit で。`claims.tex` と `references.bib` も書く |
| `append_to_record` | record への追記（append-only: 同じ id で改訂、`withdrawn` で撤回）。文献、仮説、claim、表、チャート、passage、`run_results` で run 出力から導いた結果 |
| `update_record` | `.research/results/` から各 run の結果と各 claim の verdict を導き、`values.tex` と `tables/` を描画してコミット |
| `verify_latex` | 論文をローカルでビルド（CJK は lualatex）し、未定義の引用・参照、欠けた図、エラーを報告。`local_path` を渡す。`output_path` で PDF を保存 |
| `verify_paper_values` | CI と同じ論文ゲート: 宣言、append-only の履歴、values.tex / claims.tex の再生成一致、`\airasval` の key、引用。`model` を渡すと未判定の passage 引用を判定して record に書く |
| `open_in_overleaf` | 論文をOverleafで開くリンクを作成。`local_path` を渡すと push 不要でローカルのワーキングツリーをエクスポート |
| `get_available_llms` | 設定済みキーで使える LLM プロバイダ（`model` 引数用） |

執筆ステップには 2 車線があります。skills に導かれて agent 自身が書く車線では、`get_prompts` がその step のプロンプトを返します（`hypothesis_and_design` / `experiment_code` / `experiment_analysis` / `paper_writing`、キー不要）。これらのプロンプトを共有するバックエンド LLM ツールは `analyze_experiment`（プロバイダーキーが必要）だけで、`experiment_analysis` のプロンプトに答えます。`model` 付きの `verify_paper_values` は別の引用判定プロンプトを使います。各プロンプトには作成すべきデータ形式を示す `output_json_schema` と、出力の行き先を示す `flow` が付きます。

典型的なフロー（順序と不変条件は `auto-research` skill が持つ）: `prepare_repository` → `set_github_actions_secrets` → `search_papers` → `fetch_paper_fulltext`（ファイルを読む）→ **仮説と実験設計を自分で書く**（`get_prompts(step="hypothesis_and_design")`）→ `preregister_record`（freeze commit）→ **事前登録論文を書く**（`get_prompts(step="paper_writing")`）→ `verify_latex` → staging ref に push、gate が green なら fast-forward → **実験コードを自分で書く**（`get_prompts(step="experiment_code")`、下記参照）→ `dispatch_experiment` →（`get_experiment_run_status` でポーリング）→ `import_run_outputs` → `fetch_experiment_results` → `update_record` → **分析**（`get_prompts(step="experiment_analysis")` か `analyze_experiment`）→ **図を作る**（`render_chart`、下記参照）→ **Results と Discussion を埋める** → `model` 付きの `verify_paper_values` → `verify_latex` → push。CI が再検証し、Publish Paper workflow が正式版の PDF をビルドしてコミットします。`open_in_overleaf` はユーザーが編集できる形で Overleaf に引き渡します（`local_path` 指定なら push 不要）。

### 実験コードの書き方

MCP ホストは有能なコーディングエージェント（Claude Code、Cursor など）である前提のため、AIRAS は実験コードを代わりに生成しません。`prepare_repository` の後:

1. 実験リポジトリを git でローカルに clone する
2. `get_prompts(step="experiment_code")` で契約を読む — 編集可能ファイル、CLI の形、`sanity` / `pilot` / `full` モードと検証判定行、検証が読む 3 ファイル。従うべき run id と metric は `.research/record.json` にあります
3. 設計が依存する各ライブラリについて `get_library_docs` を呼び、返される `llms.txt`（またはドキュメント）を取得して、記憶に頼らず最新のAPIをもとに実装する
4. 実験を実装し、ローカルで `mode=sanity` を実行して `SANITY_VALIDATION: PASS` が出るまで修正してから commit・push する
5. GPU 規模の実行は `dispatch_experiment` でディスパッチし、エラーと結果は `get_experiment_run_status` / `fetch_experiment_results` で取得する

ヘッドレスなパイプライン（組み込みの全自動研究ワークフロー）は従来どおり GitHub Actions 上でコードをリモート生成しますが、その経路は MCP ツールとしては公開していません。

### 図とダイアグラムの作り方

結果の図と手法ダイアグラムも、GitHub Actions ではなく MCP ホスト自身が作成します:

1. `fetch_experiment_results` で実験結果を取得する（ローカルの clone から直接読んでもよい。run ごとのディレクトリは `.research/results/` 配下にあります）
2. 結果から Vega-Lite 仕様を組み立てて `render_chart` でレンダリングし、clone 内の `.research/results/chart/` 配下に PDF として保存する。手法ダイアグラムはテキスト記法（mermaid, graphviz, d2 など）で書き、`render_diagram` で `.research/results/diagram/` 配下にレンダリングする（matplotlib などで自分で図を生成しても構いません — 重要なのは出力先だけです）
3. `render_chart` はチャートの仕様を record に追記してコミットします。コピーの手順は不要です: 論文ビルド（`verify_latex`、Publish Paper workflow）と `open_in_overleaf` が `.research/results/` と `.research/diagrams/` 配下の図PDFを自動で取り込み、LaTeX からは `images/<そのディレクトリからの相対パス>` として参照できます（例: `.research/results/chart/loss.pdf` → `images/chart/loss.pdf`。ディレクトリ構造は保持されます）。論文中の図参照はこの規約に合わせてください

`render_chart` は完全にローカルでレンダリングします。`render_diagram` はデフォルトでパブリックの https://kroki.io を使います — 未公開のダイアグラムを外に出したくない場合は `KROKI_BASE_URL` でセルフホストの Kroki インスタンスを指定してください。

コード生成と同様に、全自動研究ワークフローは従来どおり GitHub Actions 上で可視化・ダイアグラム生成を実行しますが、その経路は MCP ツールとしては公開していません。

時間のかかるステップは完了を待たず、ツール自体は即座に返ります。実験は `dispatch_experiment` の `backend` に応じて GitHub Actions または Seyval 上で実行されます。どちらも `execution_id` を返し、`get_experiment_run_status` で追跡、`import_run_outputs` で回収します。record gate・論文 gate と Publish Paper のビルドは GitHub Actions 上で実行され、`get_workflow_runs` で追跡します。

## 開発

チェックアウトからサーバーを起動する場合：

```bash
cd backend
uv sync
uv run airas
```

サーバーはstdioトランスポートを使用し、MCPクライアントがオンデマンドで起動します。データベースやWebサーバーは不要です。
